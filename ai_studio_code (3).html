Повний технічний аудит та дорожня карта шліфування архітектури Concept 2

Дата: Жовтень 2024
Об'єкт: Core-2, Stack та Skeleton
Ціль: Досягнення нульової магії, максимального DX та готовності до монорепо-структури.

Цей документ детально описує кожну знахідку, аналізує її вплив на систему та надає покрокові інструкції з виправлення.

1. StackBuilder: Порушення принципу Open/Closed та Монолітна Зв’язаність

Детальний опис проблеми

Клас StackBuilder наразі є «точкою збірки», яка знає занадто багато. Він імпортує класи Options, Builder та StackProvider для кожного розширення (Http, Database, Validation, View тощо).

З точки зору SOLID — це порушення принципу Open/Closed: система закрита для розширення без модифікації ядра пакета stack.

  • Зв'язаність: Пакет php-concept/stack має прямі залежності від усіх php-concept/extension-*.
  • Екосистема: Сторонній розробник не може написати $stack->addS3Storage(), щоб це виглядало нативно. Йому доводиться використовувати метод addCustom(), що створює «громадян другого сорту» серед розширень.

Рекомендації щодо виправлення

  • Децентралізація через Brick Registry: Впровадити механізм реєстрації «цеглинок». Кожне розширення має постачати свій Brick клас.
  • Використання Traits для DSL: Для збереження гарного Fluent API (addHttp(), addDatabase()), винести ці методи у відповідні Трейти, які підключаються до основного StackBuilder. Це дозволить фізично розділити код.
  • Динамічне розширення: Додати метод registerBrick(string $name, string $builderClass), щоб нові розширення могли «впорскувати» свої методи в Стек під час ініціалізації.

2. App::handle(): Метод-комбайн та порушення SRP

Детальний опис проблеми

Метод handle() у src/App.php виконує три не пов'язані між собою завдання:

  1. Диспатчинг: Виклик роутера.
  2. Інструментація: Вимірювання часу виконання (microtime) та піків пам'яті (memory_get_peak_usage).
  3. Події: Формування та запуск об'єкта події RequestHandled.

Це робить ядро «думним». Вимірювання ресурсів зашито в runtime, і розробник не може його вимкнути. Це також ускладнює юніт-тестування, оскільки кожен виклик handle() створює побічні ефекти у вигляді системних викликів вимірювання ресурсів.

Рекомендації щодо виправлення

  • Middleware для метрик: Всю логіку вимірювання часу та пам'яті винести в SystemMetricsMiddleware (PSR-15).
  • Чистий Dispatch: Метод handle() повинен лише отримувати об'єкти з контейнера та викликати $router->dispatch($request).
  • Event Listeners: Розрахунок тривалості та споживання пам'яті має відбуватися всередині слухача події RequestHandled, а не перед його створенням.

3. RouteStrategy: Динамічне Reflection-пекло

Детальний опис проблеми

У файлі src/Http/Routing/RouteStrategy.php метод invokeRouteCallable виконує getReflection($callable) та resolveArguments() при кожному HTTP-запиті.

Для кожного аргументу контролера запускається цикл по всіх зареєстрованих ArgumentResolvers. Якщо у вас 5 параметрів у методі та 10 резолверів — це 50 викликів методу supports() на кожен запит.

Рекомендації щодо виправлення

  • Metadata Caching (План виклику): Після першого розбору маршруту система повинна сформувати «План виклику» — масив, де вказано, який параметр контролера з якого джерела береться (наприклад: 0 => ResolverA, 1 => ResolverB).
  • Кешування плану: Цей план має зберігатися в кеші (наприклад, через extension-path-manager у папку storage/cache/routing).
  • Результат: Наступний запит до цього ж URL взагалі не повинен викликати Reflection API.

4. HttpKernelServiceProvider: Scope Pollution та небезпечний require

Детальний опис проблеми

Метод registerRoutes використовує прямий виклик require $filePath всередині циклу foreach.

  1. Scope Pollution: Будь-які змінні, оголошені у файлі маршрутів (наприклад, $router або випадкова $data), потрапляють у загальну область видимості об'єкта провайдера.
  2. Магія IDE: Файли маршрутів не мають контексту. IDE не знає, що таке $router, тому автодоповнення не працює «з коробки».

Рекомендації щодо виправлення

  • Isolated Route Loader: Створити клас-завантажувач. 
    final class RouteLoader {
    public static function load(Router $router, string $path): void {
        (static function(Router $router, string $path) {
            require $path;
        })($router, $path);
    }
}
    Це гарантує, що змінні всередині файлу маршрутів обмежені анонімною функцією.
  • Анонімні функції: Рекомендувати (або вимагати) повернення Closure з файлу: 
    // routes/web.php
return fn(Router $router) => $router->get(...);

5. resolveParameter: Відсутність Fail-Fast винятків

Детальний опис проблеми

У RouteStrategy.php метод resolveParameter повертає null, якщо жоден резолвер не підійшов. Це призводить до того, що PHP викидає TypeError під час виклику методу контролера.

  • Проблема DX: Повідомлення Argument #1 ($form) must be of type X, null given вводить в оману. Розробник думає, що проблема в даних запиту, хоча насправді проблема в тому, що в Стеку не підключено withFormRequests().

Рекомендації щодо виправлення

  • UnresolvedArgumentException: Замість повернення null, кидати типізований виняток.
  • Контекстна допомога: Виняток повинен містити текст: "Ядро не знайшло способу заповнити параметр [$name] типу [$type]. Переконайтеся, що ви активували необхідну можливість у ConceptStack (наприклад, addValidation() або addCasting())".

6. Glue Logic: Перевантаженість Ботстрапe

Детальний опис проблеми

У ApplicationStackBootstrap.php ми бачимо конструкції на кшталт створення NativeFileSessionHandler з прямим зверненням до PathManager. Це «жорстке склеювання». Якщо завтра знадобиться змінити сесію на Redis, доведеться переписувати логіку в Ботстрапі, який мав би бути лише декларативним.

Рекомендації щодо виправлення

  • Smart Builders: Методи Стеку повинні приймати лише назви («file», «redis»), а логіку створення конкретних об'єктів делегувати внутрішнім фабрикам розширень.
  • Configuration Objects: Винести логіку «якщо шлях порожній — роби так» у методи класу AppConfig. Ботстрап має виглядати як чистий список намірів.

7. ContainerDependency: Приховування помилок у getOrNull

Детальний опис проблеми

Метод getOrNull у ContainerDependency.php ловить ContainerDependencyException. Якщо сервіс зареєстрований, але його створення викликало помилку (наприклад, помилка в конструкторі сервісу), метод може повернути null, приховуючи реальну причину аварії.

Рекомендації щодо виправлення

  • Розрізнення помилок: getOrNull повинен повертати null тільки якщо сервіс фізично не зареєстрований у контейнері (!$container->has()).
  • Fail-Fast для Runtime: Будь-які помилки під час самого процесу створення об'єкта (інстанціювання) повинні прокидатися вгору, щоб розробник бачив справжній Stack Trace.

План впровадження (Roadmap)

  • Етап 1 (Монорепо): Перенести розширення в єдину структуру, щоб полегшити перехресне тестування при зміні ArgumentResolvers.
  • Етап 2 (Core Clean-up): Виправити App::handle() та resolveParameter. Це «швидкі перемоги» для стабільності.
  • Етап 3 (Performance): Впровадити Metadata Cache для роутингу.
  • Етап 4 (Stack Refactoring): Почати перехід на Traits та динамічну реєстрацію бріків у StackBuilder.
